# Lunar Landing Site Navigator — Architecture

NASA Space Apps Challenge 2026, challenge "Lunar Landing Site Navigator".

## 1. Product

A tool that lets mission planners, educators and the public **compare lunar landing
sites and dates in seconds**: where the Sun and the Earth are relative to the *real
terrain horizon*, how long until sunset / Earthset, how much solar power and
direct-to-Earth (DTE) communication a site offers, and what happens when the landing
date slips.

Design principles:

1. **Real data only.** Ephemerides come from NASA/JPL NAIF SPICE kernels (DE440 +
   lunar orientation `moon_pa_de440`). Horizons come from NASA LRO/LOLA elevation
   models. No synthetic terrain, no simulated telemetry, no made-up numbers.
2. **Zero-install, zero-backend.** The application is a static web app. Everything is
   computed in the browser from compact, pre-built data files, so it can be hosted on
   GitHub Pages and keeps working offline.
3. **Reproducible.** A Python package (`lunarnav`) downloads the NASA source data and
   rebuilds every data file the web app uses. It also is the reference implementation.
4. **Validated.** Python results are checked against the JPL Horizons API; the
   JavaScript engine is checked against Python/SPICE fixtures.

## 3. Conventions (binding for all code)

| Item | Convention |
|---|---|
| Lunar frame | Mean Earth / Polar Axis (ME), SPICE `MOON_ME` realised from DE440 (`moon_pa_de440_200625.bpc` + `moon_de440_*.tf`). Same frame as LOLA products. |
| Reference sphere | R = 1 737 400 m. Heights are metres above this sphere. |
| Latitude / longitude | planetocentric latitude, **east-positive** longitude. Public API uses −180…+180. |
| Azimuth | degrees clockwise from local north through east, 0…360. |
| Elevation | degrees above the local horizontal plane (plane normal = radial direction at the site). No refraction (no atmosphere). |
| Observer | at radius R + terrain height + observer height (default 2 m mast). |
| Time | public API: UTC as JS milliseconds since Unix epoch (`tMs`) or ISO‑8601 strings. Internal ephemeris grid: seconds past J2000 TDB (`et`). UTC → et conversion in JS is defined in §4.1. |
| Bodies | Sun radius 695 700 km, Earth radius 6 378.137 km. Positions are apparent (`LT+S`) as seen from the Moon's centre; the site offset is applied geometrically (parallax). |
| Units in files | km for vectors, m for heights, degrees for angles. Little-endian binary. |

## 4. Data contracts (files in `web/data/`)

### 4.1 Ephemeris — `ephem/index.json`, `ephem/c{K}.bin`

Uniform grid in TDB: sample `k` is at `et_k = t0_et + k * step_s`.

```jsonc
// ephem/index.json
{
  "format": "lunarnav-ephem-1",
  "t0_et": <number>,          // et of sample k = 0
  "step_s": 3600,
  "chunk_len": 8192,          // samples per chunk (≈341 days)
  "pad": 2,                   // extra samples stored before and after each chunk
  "first_chunk": <int>, "last_chunk": <int>,   // inclusive chunk indices K
  "fields": ["sun_x","sun_y","sun_z","earth_x","earth_y","earth_z","mef_x","mef_y","mef_z"],
  "tai_minus_utc": 37,
  "kernels": ["de440s.bsp", "..."], "generated": "<ISO date>", "coverage_utc": ["1969-01-01", "2060-01-01"]
}
```

* Chunk `K` holds samples `k = K*chunk_len - pad … (K+1)*chunk_len + pad - 1`
  (`chunk_len + 2*pad` records), each record = 9 × float32 in `fields` order.
* `sun_*`, `earth_*`: position of the body centre relative to the Moon centre, in the
  ME frame, km, aberration `LT+S`.
* `mef_*`: **unit** vector from Earth centre to Moon centre in the Earth-fixed frame
  (`ITRF93` where the high-precision Earth kernel covers the date, else `IAU_EARTH`) —
  used for ground-station (DSN) visibility.
* UTC → et in JS: `et = tMs/1000 - 946728000 + 32.184 + taiMinusUtc` with
  `taiMinusUtc = 37` (valid since 2017; for earlier dates the JS uses a small built-in
  leap-second table; the sub‑minute difference is irrelevant for this application but
  must be handled so that validation against SPICE passes). The ~1.7 ms TDB−TT term is
  ignored.
* Interpolation in JS: 4-point (cubic) Lagrange on each component.
* Coverage: 1969-01-01 … 2060-01-01 (Apollo era through future missions).

### 4.2 Terrain — `dem/*.json` + `dem/*.i16.gz`

Raw little-endian int16 metres above the reference sphere, gzip-compressed
(decoded in the browser with `DecompressionStream('gzip')`, in node with `zlib`).

* `dem/global.json|.i16.gz` — equirectangular (simple cylindrical), 8 px/deg
  (2880 × 1440). Row 0 is the northernmost row; pixel centres at
  `lat = 90 - (row+0.5)/ppd`, `lon = -180 + (col+0.5)/ppd`.
* `dem/south.json|.i16.gz`, `dem/north.json|.i16.gz` — polar stereographic on the
  sphere (true scale at the pole), covering at least |lat| ≥ 80°, ~240 m/px.
  `r = 2R·tan((90°−|lat|)/2)`; **south:** `x = r·sin(lon)`, `y = r·cos(lon)`;
  **north:** `x = r·sin(lon)`, `y = −r·cos(lon)` (PDS LOLA convention). Pixel
  `(row, col)` centre: `x = x0_m + col·m_per_px`, `y = y0_m − row·m_per_px`.

```jsonc
{ "format": "lunarnav-dem-1", "projection": "equirect" | "polar_stereo",
  "pole": "S" | "N" | null, "width": W, "height": H, "radius_m": 1737400,
  "ppd": 8,                                   // equirect only
  "m_per_px": 240, "x0_m": ..., "y0_m": ...,  // polar only
  "nodata": -32768, "source": "LOLA LDEM_... (PDS)", "file": "south.i16.gz" }
```

### 4.3 Horizon profiles — `horizons/{site_id}.json`

Precomputed in Python from the highest-resolution LOLA product practical for the site
(polar sites: 20 m/px or better near the site, coarser far field).

```jsonc
{ "format": "lunarnav-horizon-1", "site_id": "...", "lat": .., "lon": ..,
  "terrain_height_m": .., "observer_height_m": 2.0,
  "az_step_deg": 0.5,            // elev[i] is the horizon at azimuth i*az_step_deg
  "elev_deg": [ ...720 numbers, 0.01° precision... ],
  "max_range_km": .., "source": "LOLA ... 20 m/px (<15 km) + ... 240 m/px", "generated": ".." }
```

Horizon elevation is measured exactly like body elevation (§3): angle above the local
horizontal plane at the observer, so it is negative where the ground falls away
(dip of the horizon), and it includes lunar curvature.

### 4.5 Basemaps — `maps/`

* `maps/global_color.jpg` — equirectangular Moon albedo/colour mosaic, lon −180…180
  left→right, lat +90 top (4096 × 2048, from NASA SVS CGI Moon Kit / LROC WAC).
* `maps/global_shade.jpg` — LOLA colour-shaded relief, same grid.
* `maps/south_shade.jpg`, `maps/north_shade.jpg` — polar stereographic shaded relief
  (2048 × 2048) exactly matching the extent/orientation of `dem/south|north`.
* `maps/maps.json` — extents, projections and credits for each image.

## 5. JS engine contract (`web/js/core/`)

All modules are DOM-free ES modules that run in both the browser and node. File and
network access goes through one injectable loader:

```js
// loader(relativePath, kind) -> Promise<object|ArrayBuffer>   kind: 'json' | 'bin' | 'gz'
// web/js/core/loader.js exports browserLoader(baseUrl) and nodeLoader(baseDir).
```

### 5.1 `ephemeris.js`, `geometry.js`

```js
export class Ephemeris {
  static async load(loader)                 // reads ephem/index.json
  get range()                               // {startMs, endMs} of available coverage
  async ensure(t0Ms, t1Ms)                  // fetch chunks covering [t0,t1]; throws RangeError outside coverage
  // synchronous, valid after ensure(); out is an optional 3-element array; km, ME frame
  sunVec(tMs, out)  earthVec(tMs, out)  moonDirEarthFixed(tMs, out)
}
export function utcMsToEt(tMs)
// geometry.js
export const MOON_RADIUS_KM, SUN_RADIUS_KM, EARTH_RADIUS_KM
export function siteFrame(latDeg, lonDeg, heightM)      // -> {lat, lon, heightM, pos:[x,y,z] km, east, north, up}
export function topocentric(frame, bodyVecKm, bodyRadiusKm) // -> {az, el, rangeKm, angularRadiusDeg}
export function subPoint(vecKm)                         // -> {lat, lon} of the sub-body point on the Moon
export function stationElevation(station, moonDirEarthFixed) // -> elevation (deg) of the Moon at an Earth station
```

### 5.2 `terrain.js`

```js
export class Horizon {            // immutable
  constructor({lat, lon, terrainHeightM, observerHeightM, azStepDeg, elev /*Float32Array deg*/, source, maxRangeKm})
  elevationAt(azDeg)              // linear interpolation, wraps at 360
  static fromJSON(obj)  toJSON()
}
export class Terrain {
  static async load(loader)                       // reads only the small dem/*.json headers; grids load lazily
  async heightAt(latDeg, lonDeg)                  // metres, bilinear, best available grid
  async computeHorizon(latDeg, lonDeg, {observerHeightM = 2, azStepDeg = 1, maxRangeKm = 300} = {})  // -> Horizon
  async precomputedHorizon(siteId)                // -> Horizon | null   (horizons/{siteId}.json)
}
```

`computeHorizon` must run in < ~2 s for one site in a browser and must not block the
UI thread for longer than that (it is called from a Web Worker by the facade when
available — keep it free of DOM and of module-level state so it can be).

### 5.3 `analysis.js` and facade `index.js`

`analysis.js` holds the pure math (visible disc fraction against a horizon profile,
time series, rise/set event refinement, power model, communication model, summaries,
landing-window scans). `index.js` exposes the single object the UI talks to:

```js
const nav = await LunarNav.create({ loader });            // loads catalog, ephemeris index, DEM headers
nav.sites; nav.stations; nav.coverage                     // {startMs, endMs}
const ctx = await nav.prepare({ id?, name, lat, lon }, { observerHeightM = 2 })
      // -> { site, frame, horizon, horizonSource: 'precomputed' | 'computed' | 'sphere' }
await nav.instant(ctx, tMs, opts)     // one moment
await nav.series(ctx, t0Ms, t1Ms, stepS, opts)   // typed-array time series
await nav.events(ctx, t0Ms, t1Ms, opts)          // rise/set list, refined to ~1 s
await nav.summary(ctx, t0Ms, durationDays, opts) // KPIs for a mission window
await nav.landingWindows(ctx, t0Ms, t1Ms, opts)  // "what if the date slips" scan
await nav.yearMap(ctx, year, opts)               // day × hour visibility matrix for heatmaps
nav.subPoints(tMs)                               // sub-solar / sub-Earth points (for maps/globe)
```

`opts` (all optional): `sunMinFraction` (default 0.5 — the site counts as sunlit when
at least this fraction of the solar disc is above the terrain horizon), `commMaskDeg`
(default 2 — DTE link available when the Earth's centre is at least this far above the
terrain horizon), `panel` (`'tracking'` | `'horizontal'`, default tracking: a vertical
Sun-tracking array as used by polar landers), `stations` (ids to evaluate).

Exact return shapes are documented with JSDoc typedefs in `web/js/core/types.js`
 Every field carries a unit.

## 6. Validation strategy

| Check | Tool | Target |
|---|---|---|
| Python SPICE az/el vs JPL Horizons API (observer on lunar surface) | `python -m lunarnav validate-horizons` | < 0.01° |
| JS ephemeris + geometry vs Python SPICE fixtures (`tests/fixtures/ephem_reference.json`) | `node --test` | < 0.005° |
| JS horizon vs Python horizon on the same web-resolution DEM (`tests/fixtures/horizon_reference.json`) | `node --test` | < 0.05° RMS |
| Known facts (Apollo 11 landing Sun elevation ≈ 10.8°, lunar day length, polar Earth elevation range) | pytest + node | sanity |

Results are written to `docs/VALIDATION.md`.
